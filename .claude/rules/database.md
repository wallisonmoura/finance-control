# Database Schema

## Key tables

| Table | Purpose |
|---|---|
| `users` | Authenticated users |
| `wallets` | User financial position (bankBalance, cashBalance, receivableBalance) |
| `expense_categories` | Categories for transactions |
| `transactions` | Realized financial events — type: `INCOME` or `EXPENSE` |
| `debts` | Financial commitments — type: `ONE_TIME` or `RECURRING`, status: `PENDING` or `PAID` |

## Key constraints

- `transactions.debtId` — optional, unique. Links a transaction to the debt payment that generated it. One transaction per debt payment.
- A transaction with `debtId` is auto-generated by the debt payment flow and must not be mutated through normal Finance flows.
- All rows are scoped by `userId` — never query across users.
- CHECK constraints enforce, at the DB level, the same 5 rules already validated in the domain layer (defense-in-depth, added in `prisma/migrations/*_add_check_constraints`): `wallets.bank_balance/cash_balance/receivable_balance >= 0`; `transactions.amount > 0` and `debts.amount > 0`; `transactions.expense_category_id` required for `EXPENSE`, forbidden for `INCOME`; `debts.paid_at`/`payment_source` both null while `PENDING`, both set when `PAID`.

## User auto-provisioning trigger

`prisma/migrations/*_add_user_provisioning_trigger` adds a Postgres `AFTER INSERT ON users` trigger that creates, for every new user row: a default `Wallet` (`name = 'Main Wallet'`, `isDefault = true`, zeroed balances) and the 26 default `ExpenseCategory` rows (matching `prisma/seed.ts`'s slug list).

This is a **deliberate, owner-approved exception to RG104** (infra must not redefine central business behavior) — the trigger is the only mechanism that guarantees provisioning regardless of insert path, including a raw SQL `INSERT INTO users` run directly in the Supabase SQL editor (still the only way new users are created today, since there is no `/register` flow). See the full rationale in the migration file's header comment.

**Do not duplicate this logic elsewhere.** A future `SignUpUseCase` must NOT re-create the default wallet/categories — the trigger already covers it; adding it there too would create the row twice and violate the `wallets` `userId` unique constraint.

`tests/helpers/database/create-test-user.ts` deletes the trigger's output right after creating a test user, to preserve the pre-trigger "blank slate" contract most tests rely on. Tests that want to observe the trigger itself insert via `prisma.user.create()` directly (see `tests/integration/database/user-provisioning-trigger.int.spec.ts`).

## Production connection: pooled runtime vs. direct migrations

In production the app connects through Supabase's Supavisor pooler, split across two env vars read at different points — never merge them back into one. Naming matches Prisma's and Supabase's own documented convention for serverless deployments (their guides use these exact two names):

- `DATABASE_URL` — Supavisor **transaction mode** (port 6543, `?pgbouncer=true`), read by `src/shared/infra/database/prisma/client.ts` for the app's runtime `PrismaClient`. Connections are held only per-query, so many concurrent Vercel function invocations can share the small connection budget Supabase's plan allows.
- `DIRECT_URL` — session mode/direct connection, read by `prisma.config.ts` for the Prisma CLI (`migrate deploy`, etc.), falling back to `DATABASE_URL` when unset — which is what makes local dev/test work with a single var, since local Postgres has no pooler.

Root cause this split fixes: session-mode pooler connections are held for the whole session, not released between queries — under concurrent serverless traffic this exhausts the plan's connection cap fast (`(EMAXCONNSESSION) max clients reached in session mode`, seen in production 2026-08-19, when `DATABASE_URL` alone pointed at the session-mode pooler). Do not point `DATABASE_URL` at a session-mode or direct connection string in production, and do not point Prisma CLI migrations (`DIRECT_URL`) at the transaction-mode pooler — transaction-mode pooling doesn't support the session-level features (advisory locks, etc.) migrations can need.

**Running migrations manually against production**: since there's no automated migration step in CI/deploy, pass `DIRECT_URL` explicitly on the command line, e.g. `DIRECT_URL="<direct connection string>" npx prisma migrate deploy` — not `DATABASE_URL`, which `prisma.config.ts` now only falls back to when `DIRECT_URL` is absent.

## Homologation (hml) environment

Every non-production branch's Vercel Preview deployment connects to its own Supabase project (`finance-control-hml`), separate from production — set up 2026-08-27. This is an **optional resource, not a mandatory gate**: opening a Preview's URL to test against a real Postgres instance (instead of the local Docker DB) is worthwhile for schema changes or anything infra-adjacent, but no PR is required to go through it before merging.

- **Env vars**: `DATABASE_URL`, `DIRECT_URL`, `JWT_SECRET` (a value distinct from production's), and `JWT_EXPIRES_IN` are set in the Vercel project scoped to **Preview only** — not Production, not Development. Production's own copies of these variables must have the "Preview" scope unchecked, or Vercel refuses to let a second value be added for that scope.
- **Vercel bakes env vars into a deployment at creation time.** Changing a variable's value or scope in the dashboard does not affect Preview deployments that already exist — only ones built afterward. A stale Preview built before an env var change will keep behaving like the old configuration (this bit us once during setup: an old Preview still pointed at production's database, so a `/register` attempt failed with "email already in use").
- **Migrations**: run manually against hml the same way as production, substituting the connection string — `DIRECT_URL="<hml direct connection string>" npx prisma migrate deploy` — before relying on a Preview for a change that touches the schema.
- **No seed script**: `prisma/seed.ts`'s `assertSafeSeedEnvironment()` guard only allows a local or a `*test*`-named database, and Supabase always names the physical database `postgres` regardless of project name — so `npm run db:seed:dev` refuses to run against hml (by the same design that blocks it against production). Create test data in hml through the real `/register` flow on the Preview URL instead of loosening that guard.
